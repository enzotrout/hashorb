# 2026-07-29

## Graceful Time-Bounded Mining

Continuous mining now accepts `--max-runtime-seconds` as an optional positive
finite decimal duration up to 31,536,000 seconds. The monotonic clock begins
when the command enters its active lifecycle after configuration and backend
selection. Deadline expiry produces the successful `runtime_limit_reached`
outcome, one terminal `command_completed` event, and the same aggregate summary
and cleanup path as other controlled outcomes.

The existing SIGINT and SIGTERM scope was verified and extended with
deterministic coverage. The first signal requests cooperative stop, repeated
signals are idempotent, prior handlers are restored, and no new range or
reconnect attempt begins after the stop is observed. A non-cancellable backend
call may finish its current range before the selected backend, Stratum session,
and event sink close.

The preceding CUDA measurements recorded approximately 323.9 MH/s offline,
312.7 MH/s in a controlled CKPool test, and 311.9 MH/s across a 20-minute run
covering approximately 382.9 billion hashes. The endurance run had no
connection losses, reconnects, submissions, or command failures. Its external
timeout arrangement did not deliver a graceful terminal record and eventually
forced exit status 137, leaving JSONL incomplete. That was a process-control
failure rather than evidence of CUDA correctness or stability failure. The
internal runtime limit removes the normal bounded-run dependency on wrapper
signal forwarding.

No live Stratum command was run while implementing this milestone. The record
contains no credentials, payout address, job or run identity, work bytes,
targets, nonce or candidate material, protocol payload, or hardware identifier.

## Stale Session and Work Liveness

The clean internal-runtime CUDA endurance gate completed 360,982,285,568 hashes
across 756 ranges in 20 minutes at approximately 300.76 MH/s. It ended with
`runtime_limit_reached` and a complete terminal JSONL event after 41 received
jobs, 40 replacements, 114 work variants, and 73 extra-nonce advances. No
connection loss, reconnect, or command failure occurred.

HashOrb now offers disabled-by-default monotonic server-silence and job-age
limits. Work completion is tracked separately and cannot disguise server
silence. A configured stale transition suppresses old-session candidates and
uses the existing recovery owner for fresh subscription, authorization,
difficulty, job, and extra-nonce state. Portable socket keepalive is enabled
with OS defaults. Automatic suspend inference remains deferred because clock
behavior differs across supported platforms and ordinary scheduling gaps are
not reliable proof of suspend.

No live Stratum command was executed while implementing the liveness policy.

## DGX Spark CUDA Performance Tuning

The manually authorized five-minute liveness gate completed before tuning with
`runtime_limit_reached`, approximately 307.62 MH/s, 92.37 billion hashes, and no
connection loss, reconnect, liveness warning, stale session, or command
failure. That established that conservative liveness limits did not interfere
with a healthy session.

The original CUDA kernel rebuilt all 80 header bytes per nonce, recomputed the
fixed first 64-byte SHA-256 block, used generic byte-oriented padding for both
passes, and allocated/copied/freed five device buffers per range. Compiler
inspection reported 47 registers and a 256-byte per-thread stack frame.

The retained implementation prepares the first-block midstate and fixed tail
words on the host, specializes the 80-byte first pass and 32-byte second pass,
uses a circular 16-word schedule, and keeps derived work, candidate, and flag
buffers for the backend lifetime. Stable work skips upload; any prefix or
target change replaces the complete derived device state. The search kernel now
reports 48 registers, zero stack, and zero spills. Python still reconstructs
and independently verifies every candidate.

Same-session five-repetition offline medians changed from approximately 337.27,
325.80, 308.14, and 307.89 MH/s to 2,645.44, 2,320.72, 2,373.06, and 2,438.85
MH/s for 1-million, 10-million, 100-million, and 500-million exhausted ranges.
Nsight Systems measured the 100-million kernel at approximately 316.30 ms
before and 40.17 ms after. A later 100-repetition 500-million run sustained a
2,440.27 MH/s median. Sanitized sampling observed 55–58°C, approximately
65.9–67.5 W of GPU-reported board power, 95% utilization, and a 2,405 MHz SM
clock. No hardware or system controls were changed.

Threads-per-block values 64, 128, 256, and 512 plus several grid caps were
rebuilt and measured. Their differences were within run variation, so the
existing 256-thread and 65,535-block cap remains and no user tuning control was
added. Hardware performance counters required unavailable elevated permission;
the milestone used compiler resources, Nsight Systems timing, aggregate
telemetry, repeated benchmarks, and parity instead.

No live Stratum or CKPool command was executed during tuning. Multi-GPU,
Lite/Auto/Max/Custom profiles, Windows CUDA validation, and portable CUDA wheel
publication remain deferred, and a human-controlled post-tuning live gate is
still required.

## Post-Tuning Live Gates and Multi-CUDA Architecture

The human-controlled post-tuning gates completed before this development
milestone. The 60-second run sustained approximately 2.462 GH/s. The five-minute
run checked 737,414,244,096 hashes across 1,547 completed ranges at approximately
2.461 GH/s, within about 0.05% of the shorter run. It handled 11 jobs, 10
replacements, 178 work variants, and 167 extra-nonce advances, with no duplicate
work, connection loss, reconnect, stale session, or command failure. It ended
with `runtime_limit_reached`.

HashOrb now includes explicit `cuda-multi` orchestration. A required unique
ordinal list creates one isolated native CUDA context per device. The backend
reuses the exact native-parallel range partitioner, executes nonempty child
ranges concurrently through one persistent executor, requires full aggregate
hash accounting, and selects the global lowest Python-verified candidate. CUDA
context operations release the GIL. Any child failure closes every context and
is terminal without fallback or Stratum reconnect.

The Spark exposes one physical GPU. Its gated suite passes the isolated context
API and one-device multi-backend integration. Two paired 500-million-hash runs,
each with two warmups and seven measured repetitions, produced single-CUDA
medians of 2.443 and 2.457 GH/s and one-device multi-CUDA medians of 2.413 and
2.411 GH/s. Average median elapsed time increased by approximately 1.56%. This
is orchestration-overhead evidence, not a multi-GPU performance claim.

CPU-only wheel and source builds remain functional. The explicit `sm_121` CUDA
build imports, contains an `sm_121` cubin, and contains no home-directory path.
No live Stratum command was executed during the multi-device milestone. Real
two-device validation, profiles, Windows CUDA, and portable CUDA wheels remain
deferred.
